# Долговечная цель и усиленный контроль проблемной работы

Механика режима, в котором проблемная работа доводится до результата фоновым
продактом. Правило верхнего уровня одно и живёт в `AGENTS.md`: цель закрывается
живой проверкой пользовательского сценария через фактически установленный
продукт, а принятая корректирующая задача её не закрывает. Здесь — как это
устроено и чем проверяется.

## Зачем цель лежит на диске

Фоновое пробуждение — новый процесс каждые двадцать минут, и маршрутизатор может
отдать его другой семье моделей. Всё, что предыдущий продакт понял про работу —
что именно обещано пользователю, где путь не сходится, какая задача основная,
какого ремонта она ждёт и почему стоит, — жило в том процессе и умирало вместе с
ним. Цель сеанса памятью режима быть не может по устройству: она зеркало
активного сеанса.

Поэтому цель живёт в долговечном хранилище продукта — `content/goals/`, рядом со
снимками и портфельным планом, вне git и внутри бэкапа. Владелец записи один:
`scripts/product_goal.py`. Каждое изменение дописывается в
`content/goals/journal.jsonl`, потому что сам файл цели переписывается целиком, а
«кто, когда и по какому наблюдению перевёл цель в паузу» — вопрос о прошлом.

Второй технической машины состояний тут нет. Задачи, прогоны, ревью, гейты и
жизненный цикл остаются в контуре разработки; цель держит продуктовую сторону и
ссылается на номера задач для всего технического.

## Когда режим включается

Обычная работа его не получает: прошла без замечаний либо не более чем за два
содержательных круга ревью и без отказов штатного хода. Включает контроль любой
из шести признаков отклонения, названных пользователем:

| признак | чем наблюдается |
| --- | --- |
| `third_review_round` | `reviews/rounds.jsonl` задачи, поле `round`; запасной источник — строки «Review round N» её `trace.md` |
| `repeat_finding` | `repeated_finding_ids` в `reviews/rounds.jsonl` |
| `launch_refused_again` | строки об отказе запуска в `trace.md` задачи |
| `manual_bypass` | записывается продактом с наблюдением |
| `corrective_task` | заведение корректирующей задачи по этой цели |
| `version_divergence` | записывается продактом с наблюдением |

Первые три и шестой снимаются механически: `product_goal.py observe` читает
артефакты самой задачи на каждом пробуждении и дописывает найденное. Два
оставшихся требуют суждения, поэтому записываются продактом — и обязательно с
источником: признак без наблюдения не записывается вовсе, иначе режим включался
бы по настроению и на обычной работе.

Два круга — порог контроля, а не предел исправлений. Число кругов и правок не
ограничивается ничем.

## Что цель держит и чем закрывается

Запись цели отвечает на шесть вопросов: какой пользовательский результат обещан,
по каким наблюдаемым условиям он считается достигнутым, какая задача основная,
какие корректирующие заведены и приняты, где сейчас ближайший разрыв и что
следующий переход. Плюс причина паузы, если работа на паузе.

Три правила стоят в коде, а не в промпте, потому что промпт — это то, чему новый
сеанс может и не последовать:

- корректирующая задача заводится только из явной паузы и только с ожидаемым
  пользовательским эффектом и наблюдаемым критерием возврата к основной работе;
- приёмка корректирующей задачи цель не закрывает и требует, чтобы задача
  наблюдалась завершённой; после неё основная работа возвращается командой
  `resume`, и без этого цель не закрывается;
- `close` требует живой проверки и того, чем она наблюдена, отказывает при
  незакрытых ремонтах и при основной задаче не в статусе `completed`. Коммит,
  тест, принятое ревью и статус завершения закрывающим свидетельством не
  считаются.

## Команды

```bash
python3 scripts/product_goal.py open --thread <тред> --outcome "..." \
    --observable "..." --main-task <N> [--gap "..."] [--next "..."]
python3 scripts/product_goal.py list [--thread <тред>] [--json]
python3 scripts/product_goal.py observe [<id>]          # снять признаки с артефактов
python3 scripts/product_goal.py set <id> --gap "..." --next "..."
python3 scripts/product_goal.py pause <id> --reason "..." --src "..."
python3 scripts/product_goal.py corrective <id> --task <N> --effect "..." \
    --return-criterion "..."
python3 scripts/product_goal.py accept <id> --task <N> --src "..."
python3 scripts/product_goal.py resume <id> [--gap "..."] [--next "..."]
python3 scripts/product_goal.py close <id> --live-check "..." --src "..."
```

## Где это видно

- **Пробуждение.** `thread_tick.py` читает активные цели направления до решения
  о запуске и кладёт их в промпт отдельным блоком: по каждой активной цели
  обязателен либо запущенный следующий безопасный шаг, либо названный вслух
  конкретный внешний блокер.
- **События.** Включение усиленного контроля и смена состояния цели — переходы,
  как всякие другие. Цель, по которой ничего живого не идёт, — стоячее
  состояние, как «идёт простой»: повторяется не чаще
  `PRODUCT_OWNER_GOAL_REMIND_SECONDS`, а изменившаяся цель — новость сразу.
- **Файл состояния направления.** `state/threads/<тред>.json`, поле `goals` —
  снимок целей на момент проверки, записанный независимо от того, разбудили
  кого-нибудь или нет.
- **Панель.** Колонка направления показывает цель в шапке, рядом с проверкой:
  обещанный результат, пометку усиленного контроля, ближайший разрыв, основную
  задачу и её паузу, корректирующие задачи с их состоянием и следующий переход.
  Контракт снимка это проверяет: цель без источника, с неизвестным состоянием
  или с корректирующей задачей без критерия возврата на панель не попадает.

## Спящий терминал не держит фоновую цель

Уступать дорогу другому продакту надо, только пока тот может занять то же
рабочее дерево **и действительно работает**. Открытый терминал, которому работу
уже передали, иначе держал бы фоновую цель ровно столько, сколько существует
процесс, — а это и есть то самое «мне приходилось следить за доступностью
терминала», от которого режим избавляет.

Наблюдение — разница процессорного времени процесса между двумя наблюдениями
тика (поля 14 и 15 `/proc/<pid>/stat`). Сеанс, который разговаривает с моделью,
жжёт секунды процессора между пробуждениями; оставленное окно не жжёт ничего.
Порог и окно измерения — `PRODUCT_OWNER_OWNER_CPU_TICK_SECONDS` и
`PRODUCT_OWNER_OWNER_IDLE_SECONDS`. Первое наблюдение процесса разницы не имеет и
считается работой: сомнение решается в пользу уступки. Записывает наблюдение
только тик (`state/process-inventory/owners.json`) — панель перестраивается
каждые несколько секунд, и измеренная по ней разница объявила бы неработающими
всех. Кому дорогу не уступили, видно на диске: `not_yielded_to` в
`yielded_to_awake_owner` файла состояния направления.
