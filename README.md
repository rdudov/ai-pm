# ai-pm

Дом продуктового агента: правила его работы, наблюдение направлений, тик
пробуждения, дверь письма с порогом отправки и доска процесса. Здесь нет ни кода
продуктов, ни правил исполнения задач — они живут в системе задач, куда работа
реально уходит.

Живое содержание одной установки — снимки продуктов, портфельный план, решения,
уроки и карта её направлений — намеренно лежит вне git. Ядро переносимо; то, что
эта установка знает про своего пользователя, остаётся у неё.

## Установка

Нужен Python 3.12 и система задач рядом — публичный
[task-agent](https://github.com/rdudov/task-agent) или установка на его основе:
продакт наблюдает работу, которая идёт там, и сам её не исполняет.

```bash
git clone <этот репозиторий> ai-pm && cd ai-pm

# 1. Файл этой установки: где стоит система задач, куда уходят письма,
#    какие есть направления и какими репозиториями каждое владеет.
cp threads.example.json threads.json && $EDITOR threads.json

# 2. Долговечное хранилище продуктового содержания и первый продукт по шаблону.
python3 scripts/product_memory.py --init --start-product мой-продукт
$EDITOR content/products/мой-продукт/snapshot.md
python3 scripts/product_memory.py --check

# 3. Наблюдение направления и доска.
python3 scripts/thread_state.py <ключ направления> --format text
python3 scripts/process_map_serve.py --out board.html   # или --serve 8765

# 4. Одно пробуждение вручную; дальше его ставит таймер.
python3 scripts/thread_tick.py <ключ направления> --dry-run

# 5. Защита перед каждым push: этот репозиторий публичный, а живёт в нём
#    рабочий дом продакта.
git config core.hooksPath hooks
$EDITOR state/private-history-markers   # по имени в строке, см. ниже

# 6. Личность коммитов этого репозитория — публичная, а не ваша почтовая.
git config user.name  "ai-pm"
git config user.email "ai-pm@users.noreply.github.com"
```

**Проверка перед push — обязательный шаг установки, а не украшение.** Публичный
репозиторий, в который продакт коммитит каждый день, отделяет от утечки одна
привычка — `.gitignore`; одного `git add -f` хватает, чтобы её обойти. Поэтому
`hooks/pre-push` спрашивает владельца проверки в системе задач
(`skills/repo-health/scripts/check_pre_push.py`) про исходящие изменения и
отклоняет push, если в них есть приватный путь, похожий на секрет ключ, лишняя
ссылка или имя из вашего списка. Список — `state/private-history-markers`, по
имени в строке; он вне git, потому что список приватных имён сам приватен.
Закрыто по умолчанию: нет системы задач рядом, нет её проверки, нет списка имён
или проверка старше, чем нужно (не умеет сравнивать с приватными именами), —
push отклоняется, а не проходит молча. Если ваша система задач держит именно
такую старую копию, назовите ключом `leak_check_repo` установку, где проверка
новее; по умолчанию это та же установка, что `tasks_repo`. Отрицательный
контроль (подсадить утечку и убедиться, что push не уходит) стоит прогнать один
раз при установке.

**Личность коммита уезжает наружу так же, как файл.** Имя и адрес автора и
коммиттера лежат в самом объекте коммита, куда никакой файловый скан не
заглядывает, поэтому hook сверяет со списком приватных имён ещё и личность и
сообщение каждого исходящего коммита. Отсюда шаг 6 установки: у публичного
репозитория своя публичная личность, а не ваш почтовый адрес из `~/.gitconfig`.
Отказ называет коммит и поле, но никогда — само найденное значение: печатать
приватное имя в терминал и в журнал CI означает опубликовать его ещё раз.
Уже сделанный коммит с личной почтой правится `git commit --amend --reset-author`
(последний) или `git rebase`, и только потом уходит наружу.

У публикующего checkout должен быть ровно один remote. Проверка отклоняет push
из клона, который держит ссылки второго remote, — так она не даёт нечаянно
отзеркалить наружу чужую историю. Если вы переехали сюда из другого
репозитория, старый remote надо удалить, а не оставить рядом.

Пробуждение по расписанию — два юнита из `systemd/`: шаблон
`product-thread@.service` с рабочим каталогом установки, его таймер и по одному
`product-thread@<направление>.timer.d/offset.conf` на направление, чтобы они не
просыпались в одну секунду. Пример смещения лежит рядом.

Отказы этого пути названы словами, а не трассировкой: нет хранилища — «долговечный
корень недоступен», не назван корень системы задач — «система задач не
наблюдается». Пустой ответ вместо отказа был бы враньём: ненаблюдаемое — это не
то же самое, что пустое.

## Проверки

```bash
cd scripts && python3 -m unittest discover -s . -t . -p 'test_*.py'
```

Стандартной библиотеки хватает почти на весь набор. Два модуля —
`test_product_memory.py` и `test_rules_guard.py` — написаны в стиле pytest
(фикстуры, `parametrize`), поэтому без `pip install pytest` они не
импортируются, и `unittest` показывает по ошибке на каждый; сам продакт pytest
не требует ни для чего. Полный набор:

```bash
pip install pytest && cd scripts && python3 -m pytest
```

Отдельно живут две проверки, которые полезно звать руками:
`python3 scripts/rules_guard.py --guard` — что в `AGENTS.md` не завёлся
временный план, и `python3 scripts/runner_contract.py` — что имена, которые
наблюдение берёт у системы задач, всё ещё на месте.

## Что здесь есть

- `AGENTS.md` — роль, правила разговора с пользователем, границы. Единственный
  канонический текст про то, как продакт работает. Только устойчивые правила:
  порядок работ, паузы и датированные планы туда не пишутся, у них другой
  владелец. Держит это `scripts/rules_guard.py --guard`.
- `content/` — живое продуктовое содержание этой установки, намеренно вне git:
  продуктовое обсуждение не имеет права менять проверяемое дерево, пока по нему
  идёт техническое ревью. Внутри — снимок продукта
  `content/products/<slug>/snapshot.md` (концепция, пользовательские пути с
  состоянием, текущая ставка, «не делаем», журнал эффекта, открытые вопросы),
  его история и вложения, кросс-продуктовые решения и одна текущая редакция
  портфельного плана. Состояние пути меняется только по артефакту задачи или
  живой проверке. Единственная долговечная копия — ночной бэкап, и он обязан
  отказать, если корень исчез.
- `scripts/product_memory.py` — владелец этого хранилища: чтение снимков,
  независимые записи и вложения, редакции плана с отказом при конкурентной
  публикации, `--check` целостности. Порядок работ между продуктами задаёт
  `--plan`, а не статус задачи.
- `content/goals/<id>.json` — долговечные цели проблемной работы, рядом с
  журналом `journal.jsonl`. Владелец записи — `scripts/product_goal.py`: он
  держит обещанный пользователю результат и наблюдаемые условия его достижения,
  основную и корректирующие задачи, ближайший разрыв, причину паузы и следующий
  переход, снимает признаки отклонения с артефактов самой задачи и отказывает
  закрыть цель без живой проверки установленного продукта. Устройство режима —
  `docs/goal-control.md`.
- `products/<slug>/product.md` — прежние монолиты установки, если она пришла с
  них. Остаются на диске как датированный архив миграции и путь отката, из git
  убраны, никем не читаются; расхождение с описью переноса показывает
  `product_memory.py --check`.
- `threads.json` — файл установки: где стоит система задач, куда уходят письма,
  какие есть направления фоновой работы и какими репозиториями каждое владеет.
  Вне git; его форма — `threads.example.json`.
- `scripts/thread_state.py` — наблюдаемое состояние направления: живые прогоны
  по pid, свежесть прогресса по mtime, статусы задач, коммиты. Транскрипты
  детей не читаются: тик стоит одинаково независимо от объёма работы.
- `scripts/thread_tick.py` — одно пробуждение. Будит продакта на переходе и на
  трёх состояниях, которые переходом не являются: простой при непустой очереди,
  недоставленный документ старше порога и долговечная цель, по которой ничего
  живого не идёт. Активные цели читаются до решения о запуске и кладутся в
  промпт. Пишет в `state/threads/<тред>.json` блок `check` — когда проверял,
  когда проверит снова, чем кончилось и почему — и поле `goals` со снимком
  целей направления. Дорогу уступает только работающему продакту: у бодрствующих
  наблюдается разница процессорного времени между двумя тиками, и спящий
  терминал, которому работа уже передана, попадает в `not_yielded_to`, а не
  останавливает фоновую работу.
- `scripts/goal_session.py` — одна продолжающаяся фоновая продуктовая сессия под
  усиленной целью. Пока цель не разрешена, направление ведёт она, а не новый
  сеанс на каждом тике: один и тот же разговор (`--resume`), наблюдение каждые
  полминуты, ход модели — только на значимое изменение. Контрольный снимок
  `state/goal-sessions/<тред>.json` держит идентификатор разговора и по каждому
  ходу — причину, время реакции, учёт кеша, пересборку стартового контекста и
  пост-контроль стоячей цели. Тик при ней watchdog: не поднимает второго
  продакта поверх живой сессии и восстанавливает её после смерти или
  вынужденной ротации — но уступает только наблюдаемо живой сессии, а стоячую
  цель, которую вести некому (например, маршрут ушёл к Codex), ведёт сам.
  Устройство — `docs/goal-control.md`.
- `scripts/outbound.py` — единственная дверь, через которую письмо уходит
  пользователю. Порог: письмо идёт, когда нужен выбор пользователя, изменилась
  польза (раздел «Пользовательские пути» снимка продукта) или закончилась
  заказанная работа с документом. Прогон стартовал, прогон закончился,
  репозиторий двинулся — не письмо, а пуш и табло; пуш при этом не ограничен
  ничем. Однотипное склеивается по содержанию, а не по теме, и накопленное
  уходит одним сообщением с ближайшим письмом или само по себе через
  `PRODUCT_OWNER_HOLD_MAX_SECONDS`. Перед отправкой читаются два источника
  «что пользователь уже слышал»: реестр отправленного `state/outbound.json` и
  стенограммы CLI тех сессий, где говорил человек. Вопрос пользователю решается
  раньше всех трёх правил и не может быть ни склеен, ни отброшен.
  Вопрос узнаётся тремя независимыми признаками, и любого одного хватает:
  строка `ВОПРОС: да` от сочинителя письма, старая метка `ПОВОД: вопрос` и сам
  текст — знак вопроса или просьба выбрать, чем бы она ни кончалась. `ВОПРОС:
  нет` не заглушает ничего: сочинитель — модель, она ошибается в метке, и
  сомнительный случай остаётся вопросом. До 2026-08-09 текстовым признаком была
  одна пунктуация, и «Пожалуйста, выберите: …» с точкой на конце вопросом не
  считалась.
  Ответ на входящее письмо — явный вид `reply`, который ставит почтовое
  пробуждение вместе с исходным Gmail id. Он проходит той же дверью, но всегда:
  порог инициативной почты, сверка с чатом и склейка к ответу не применяются;
  журнал сохраняет id исходного и отправленного сообщений.
  Реестр держится под блокировкой на отдельном файле `state/outbound.lock`,
  который никогда не подменяется; сами данные читаются уже под блокировкой, а
  временный файл при фиксации именуется по писателю. Блокировка на самом реестре
  четыре таймера направлений не сериализовала: писатель, ждавший на подменённом
  inode, затирал чужую запись вместе с удержанным вопросом.
  Рядом ведётся `state/outbound.backup.json` — копия последнего зафиксированного
  состояния, из которой реестр восстанавливается, если пропал или испорчен, с
  видимой отметкой `recovered_at`; намеренный сброс — это удаление обоих файлов.
  Каждое решение шлюза дописывается в `state/outbound-journal.jsonl`, потому что
  `state/threads/<тред>.json` переписывается целиком на каждом тике и хранит
  только последнее.
- `scripts/claude_product_owner.py` — единая точка запуска продакта для
  интерактивного `claude-pm`, тиков и почты. Она сравнивает наблюдаемые остатки
  недельных окон Claude и Codex и выбирает семью с большим остатком. Внутри
  Claude выбирает Fable только когда отдельный опубликованный остаток Opus
  строго меньше 5%; общий пятичасовой или недельный лимит не выдаёт за
  Opus-лимит. Если один из недельных остатков прочитать нельзя, процент не
  выдумывается, отказ называется в маршруте и сохраняется Opus. Снимок Codex
  принимается только из явно семидневного окна с наблюдаемым временем события,
  пока его граница сброса не прошла.
- Пуш о ходе работы фоновый тик отправляет через bot transport системы задач,
  если он там установлен. Токен и разрешённый адрес читает он сам, из своего
  серверного владельца: systemd-юниту не нужны копии секретов, ручные экспорты
  или адрес в argv. Установка, где такого транспорта нет вовсе, — рабочая: её
  новости приходят письмом и стоят на доске.
- `systemd/product-thread@.service` и `product-thread@.timer` — шаблон
  пробуждения, а `systemd/product-thread@<тред>.timer.d/offset.conf` — своё
  время для каждого направления. Ставится в `/etc/systemd/system/` и
  подхватывается `systemctl daemon-reload`; шаблон юнита остаётся общим.
  В git лежит пример `product-thread@example.timer.d/offset.conf`, а смещения
  реальных направлений принадлежат установке.
- `scripts/process_map_state.py` — снимок контура для внешнего показа. Собирает
  наблюдаемое: статусы, живость прогонов, исполнителя и роль из `status.json` и
  событий dev-pipeline, причину, по которой задача стоит, давность последнего
  изменения области, каналы связи и состояние репозиториев. Порядок работ он не
  выводит, а читает: очередь и паузы приходят из действующей редакции
  портфельного плана (`plan_projection`), потому что владелец порядка — план.
- `scripts/process_map_schema.py` — контракт снимка и ленты и **единственный
  владелец обезличивания**. Он ничего не читает с диска, поэтому очистка
  доступна и сборщику, и писцу, и рендеру, не ломая границу рендера. Здесь же
  живёт `startable()` — «эту задачу ничто наблюдаемое не держит», один предикат
  на два вопроса: будить ли направление и предлагать ли «продолжить сейчас».
- `scripts/process_map_serve.py` — доска и список задач: собрать состояние и
  построить экран. `--out board.html` — самодостаточный файл, открывается
  двойным кликом без сети; `--serve 8765` — живой режим, свежий снимок на каждый
  запрос. Единственный компонент, который видит и сборщик, и рендер. Он же
  зовёт писца — не чаще, чем раз в `PRODUCT_OWNER_TIMELINE_TICK_SECONDS`
  (по умолчанию 60) и после отправки ответа, — и он же принимает `POST /wake`.
- `scripts/process_map_render.py` — рендер. Принимает только готовый JSON
  (`--snapshot`) и не импортирует сборщик, поэтому «картинка не покажет того,
  чего не видела» — свойство входа, а не дисциплины автора.
- `scripts/process_map_recorder.py` — писец: наблюдаемые изменения в ленту
  `state/timeline.jsonl`. Журналы читаются от байтового смещения, транскрипты
  детей — никогда. Отдельной долгоживущей единицей он не работает: его зовёт
  доска, пока на неё смотрят, и первый заход после перерыва досыпает пропущенное
  настоящими наблюдёнными временами. Каждая запись помечается временем того
  файла, из которого она прочитана: смена статуса — временем записи `task.md`,
  артефакт — своим mtime, коммит — датой коммита. Времени взгляда в записи не
  бывает: пока смена статуса помечалась им, перерыв в наблюдении превращал
  недельной давности завершения в сегодняшние новости и вытеснял из ленты
  действительно свежее.

## Что доска обещает и чего не обещает

Правила, на которых держится правдивость экрана. Менять их — значит менять
названного владельца, а не подкручивать вывод.

- **Ничего не названо без того, чем оно наблюдено.** Исполнитель, роль, причина
  затора, давность и живость прогона имеют парное поле-источник; названное без
  источника не проходит валидацию снимка. Пустая клетка честнее уверенной догадки.
- **Задача стоит в колонке того направления, чей проект она назвала.** Задачи
  направления собираются двумя вопросами к одному индексу: по его проектам и по
  его поисковым словам из `threads.json`. Поисковое слово — страховка для
  задачи, которую никто не связал с проектом, и объявленную связь оно не
  перевешивает: строка, чей проект принадлежит другому направлению, остаётся у
  того направления. Иначе догадка по буквам спорит с объявленной связью и
  выигрывает — 14 августа `task_search: ["max"]` направления «Клиент» совпал со
  слагом `1172-…-takes-max-at-once`, где `max` — это «максимум» из заголовка, и
  живой прогон Платформа был показан как текущая работа «Клиента» сразу в
  двух колонках. Цена правила названа: задача, которую по имени ждёшь у одного
  направления, а по объявленному проекту она у другого, видна там, где её
  проект; лечится это в задаче, а не в доске.
- **Сверху — ответы, ниже — подробности.** Порядок страницы такой: полоса-сводка,
  колонки направлений, очередь плана, лента наблюдений, подвал. Первый экран на
  окне 1440×900 отвечает на четыре вопроса пользователя: что идёт прямо сейчас,
  что стоит и почему, что дальше по каждому из четырёх направлений и что
  требуется лично от него. Лента изменений и очередь плана стоят ниже: это
  история и подробность, а не ответы, и до задачи 1163 они занимали весь первый
  экран — колонки начинались на 2300-м пикселе, а вся страница была 30 листами
  A4. Сколько записей ленты осталось за пределом, по-прежнему сказано, но за
  переключателем источников.
- **Шапка говорит две вещи: когда собрано и что требуется от человека.** «В
  работе N» из неё убрано: это было число без подлежащего, а тот же факт с
  именем задачи, автором и возрастом стоит на двести пикселей ниже, в
  полосе-сводке. «Требуется от вас» осталось — единственная строка, обращённая к
  человеку, и набрана она отдельным весом и цветом. Значка режима нет: живой
  режим — наш режим, а не его. Наше собственное нерешённое («решает продакт: N»)
  видно по кнопке «Показать источники» и областью «Решает продакт» своей
  колонки: это работа продакта, а не долг человека.
- **Каждое направление говорит своё состояние одной строкой.** «Идёт / ждёт
  вашего решения / простаивает / на паузе / стоит в очереди / стоит / свободно»,
  за словом — чем оно наполнено, ниже — причина обычными словами и ближайшая
  работа. Здесь стояли шесть равновесных чисел, из которых большинство нули, а
  первое («задач 228») считало за всё время и не сходилось ни с суммой колонок,
  ни со счётчиком вкладки «Задачи». Все три числа остались, и каждое теперь
  подписано тем, что считает. Строка собирается из полей, которые сборщик уже
  отдаёт: областей колонки, `startable`, причин простоя последней проверки и
  слова плана на плашке; ничего нового не наблюдается.
- **Простой при доступной работе называется простоем.** Порядок ветвей строки
  состояния — это порядок важности для человека, а не порядок областей:
  «простаивает» стоит выше «стоит», потому что пятнадцать заторов не отменяют
  того, что запускать есть что и не запущено. Заторы называются тут же, строкой
  ниже.
- **Экран один — доска, плюс вкладка «Задачи».** Переключателя «Доска / Карта»
  нет, и самого экрана изометрической карты (задача 726) тоже: её единственным
  входом был этот переключатель. Лента наблюдений, которую карта проигрывала,
  осталась и получила нового читателя — ту самую ленту сверху доски.
- **«Продолжить сейчас» будит владельца, а не запускает задачу.** Кнопка стоит в
  шапке колонки, под строкой состояния направления, в каждом из четырёх
  направлений и в любом состоянии. Условия «показывать, когда проверка имеет
  смысл» больше нет: оно означало `!live && startable > 0`, то есть на живой
  доске 14 августа кнопка была ровно в одной колонке из четырёх, и пользователь
  сказал прямо: кнопки «Продолжить» там нет. Там, где начинать нечего, кнопка
  не исчезает молча, а говорит, чего не хватает; пока проверка идёт, она
  недоступна и говорит об этом. Что стоит и почему, надпись под кнопкой не
  повторяет: «живых прогонов нет, а ничто не держит задач: 10» стояло в колонке
  дважды — строкой состояния и ещё раз под кнопкой, — и число осталось в одном
  месте, а кнопка отвечает на свой вопрос: что сделает нажатие. Отказ сервера тоже говорит по-человечески, а
  ответ systemd стоит рядом за переключателем источников. Нажатие просит сервер
  доски запустить
  `product-thread@<тред>.service` — ту же единицу, которую заводит
  двадцатиминутный таймер. Отсюда и обещание «двух продактов не будет»: systemd
  не держит двух экземпляров одной единицы, поэтому повторный клик и совпавший
  по времени фоновый тик — это одна проверка. Своей очереди, замка и надзирателя
  доска не заводит. Чем проверка кончилась, говорит та же строка «прошлая …»,
  которую пишет тик; «запрос принят» стоит до появления этой записи и уходит с
  ней. Право на действие не шире права на саму доску: сервер слушает только
  петлю, запрос с чужой страницы отбивается по `Origin`/`Sec-Fetch-Site` и по
  типу содержимого, а имя направления проверяется по `threads.json`. Таймер
  остаётся страховкой: браузер не становится условием автономной работы.
- **Вкладка «Задачи» — визуализация существующего индекса, а не новый реестр.**
  В списке есть все известные индексу номера, названия и статусы; поиск принимает
  полный или частичный номер (с `#` или без него) и часть названия. Индекс остаётся
  lookup-слоем: карточки строятся из каталогов задач при первой загрузке и едут в
  том же единственном JSON, который уже получает рендер. Поэтому десятисекундный
  опрос обновляет лёгкий индекс, не переносит детали тысячи каталогов заново и не
  заводит вторую дверь к диску. Самодостаточная запись сохраняет и список, и детали.
- **Аппарат происхождения — за одним переключателем.** «Источник», «Поле
  редакции», «Сверка», «также названы», «наблюдено по mtime», правило отбора
  области, внутренности планировщика и счёт задач за всё время скрыты по
  умолчанию и включаются кнопкой «Показать источники» в шапке — одной на всю
  страницу, со своим состоянием в `sessionStorage`. Ничего из этого не удалено:
  доска по-прежнему может показать, чем наблюдено каждое своё утверждение. Повод:
  одна и та же фраза сверки стояла на экране двадцать три раза подряд, а
  пользователь читает доску не для того, чтобы её проверять.
- **Ни один видимый блок текста не длиннее трёх строк.** Длинный текст — цель,
  строка плана, причина, вывод проверки, название задачи — складывается общей
  механикой `.fold`: три строки и кнопка «показать целиком», раскрытие на месте.
  Обрезки многоточием на доске по-прежнему нет нигде: текст не теряется, он
  сложен. Колонка Продукт выводила около полутора тысяч знаков прозы цели с путями
  файлов и `journalctl` — это и есть то «вчитываться в прозу», о котором писал
  пользователь.
- **Ни английской строки, ни сырого markdown в том, что видно без раскрытия.**
  `**жирный**`, `~~зачёркнутый~~` и обратные кавычки снимаются одной строкой
  внутри `human()`: страница печатает текстовые узлы, поэтому разметка доезжала
  до экрана символами. Строку хода работы ребёнок-исполнитель пишет себе, и на
  плашке она стоит за переключателем источников. Там же, где чужая строка стоит
  ответом на вопрос — причина затора в полосе и в колонке, подпись записи в
  ленте, — доска не переводит её (это было бы выдумыванием факта) и не оставляет
  как есть: на экране остаётся то, что написано читателю, а остальное уезжает за
  тот же переключатель, и о том, что там есть ещё, говорит многоточие.
  Решается это про предложение, а не про строку целиком: русская вводная не
  может протащить на экран английский хвост («получить из офисного контура commit
  engine, commit API, собранный image и один живой trace»), а одно машинное имя
  в середине не уносит за источник читаемый русский абзац. Порогов два. Первый —
  три латинских слова подряд: так ловится и целиком английский вердикт, и
  английская проза внутри фразы. Второй — имя, написанное машине, то есть два
  куска латиницы через подчёркивание (`f_003_closure_records`,
  `probe_model_provenance`): такое имя остаётся на экране, только если фраза
  вокруг него всё-таки русская, — «Нужно ли закрыть `verification_gap` задачи
  495?» это вопрос о предмете, а «Кандидат: pass36_repaired_git_…» — имя с
  русской наклейкой. `progress.json`, `journalctl`, слаг `example-product` и
  `#1163` остаются на месте: это имена, а не проза. Ту же границу проходит вопрос
  области «Решает продакт» — его пишем мы сами и как придётся; вопрос к человеку
  через неё не идёт, потому что «что требуется лично от вас» — первый вопрос
  доски, и заменить его фразой значило бы на него не ответить.
  Когда показать нельзя ни одного предложения, на месте причины стоит не
  сообщение о том, что причина где-то есть, а то, что уже наблюдено и уже
  написано по-русски: вердикт проверяющего с числом находок, счёт непройденных
  гейтов, врущий ярлык, записанное состояние. Отсылка к словам автора остаётся
  хвостом после этой фразы. Заглушка вместо ответа — это то же «пусто», только
  вежливое: пользователь спрашивает «где затор и почему», а получает сообщение о
  том, что ответ есть где-то ещё.
  Своё доска до порога не доводит: причину «не пройдено гейтов: 3» она пишет
  сама, а имена непройденных гейтов ставит в её источник — на первом экране
  стояло «гейты не пройдены: f_003_closure_records, documentation_consumers_agree»,
  и разбирал это глазами человек. По той же причине имя непрерывной сессии ушло
  из записи двадцатиминутного тика: «не будился: направление ведёт непрерывная
  сессия b214f99e-… (ходов 48)» писал сам тик, и UUID стоял на первом экране —
  теперь он остаётся в самой записи (`goal_session.session.id`), которую доска и
  так называет источником.
- **Пустая область не занимает экран.** Область без содержимого не печатает ни
  заголовка, ни слова «пусто»; сколько их и какие — одной свёрнутой строкой внизу
  колонки. На живом состоянии пустыми были около тридцати пяти блоков из сорока
  восьми, и каждый занимал высоту.
- **Очередь читается как очередь.** В показанной голове списка нет строк, все
  задачи которых по наблюдению уже сделаны: они уходят в хвост, который
  раскрывается кнопкой «показать все N» — кнопкой, а не серой сноской «ещё строк
  редакции: 19», которую никто не нажимал. Место в очереди считается по редакции
  плана, а не по остатку после отбора, и у каждой строки видно направление.
- **Доска называет ревизию, на которой работает.** В подвале — короткий хэш
  HEAD, прочитанный при старте процесса, и рядом хэш рабочего дерева, если они
  разошлись. Служба держит свой Python в памяти с момента запуска, а шаблон
  страницы читает с диска на каждый запрос: 14 августа из-за этого полчаса
  показывалась страница нового шаблона на старом сборщике, и понять это можно
  было только расследованием. Порядок от этого не меняется — после правки доски
  службу перезапускают, — но теперь служба, которую не перезапустили, говорит об
  этом сама.
- **Живой прогон сильнее записанного статуса.** Признак живости наблюдается по
  процессу независимо от того, что стоит во frontmatter, и задача с живым
  прогоном стоит в «В работе сейчас» при любом статусе; расхождение названо на
  самой плашке словами «статус говорит „завершена“, а прогон идёт: запись
  устарела». Повод: 14 августа в 10:41 колонка «Клиент» показывала «в работе 0 —
  пусто», тогда как круг 5 по задаче 1151 шёл с 10:18 — во frontmatter оставался
  `completed` от прежнего преждевременного закрытия. Тик считает живые прогоны по
  процессу и всегда считал; расхождения двух ответов на один вопрос больше нет.
- **Служебные `TEST`-задачи в список для человека не попадают.** Каталог знает
  фикстуры, которые оставляют наши же прогоны контура; вкладка «Задачи» — это
  список работ, и строка в нём стоит ровно столько, сколько стоит доверие к
  тому, что каждая строка — настоящая работа.
- **Полоса называет ровно столько, сколько даёт прочитать целиком.** У каждого
  названного в верхней полосе затора причина видна полностью — без многоточия,
  без обрезки по числу строк и не под наведением мыши. Короткой полосу держит не
  обрезание уже обещанного ответа, а число имён: рендер берёт имена, пока их
  причины укладываются в `STRIP_GROUP_CHARS`, и вслух пишет «ещё N — в колонках
  ниже». Граница измерена браузером на 1440×900 и 390×844; менять её — значит
  заново мерить на телефоне, а не подбирать на глаз (находка HIGH-1 ревью 789:
  полоса называла четыре затора и давала прочитать причину одного).
- **«Ждёт решения пользователя» — это спрошенное у него и неотвеченное.** Два
  наблюдения, и оба в тексте самой строки или в файлах на диске: в строке стоит
  пометка «Спрошено у пользователя <дата>, письмо/Telegram <идентификатор>», и
  после этой даты ответа не наблюдалось — ни письма пользователя в том же треде
  (`.state/gmail/product-owner/`), ни решения, записанного в самой строке.
  Владелец признака один — `question_entry()`, и через него проходят и вопросы
  задач, и вопросы продуктов, поэтому «чей это вопрос» на всём экране значит
  одно и то же. Всё остальное — наши вопросы, и они стоят в области «Решает
  продакт»: ничего не прячется, но и не выдаётся человеку за его долг.
  `blocked` — это «Затор», а не долг человека.

  До правки областью владело «есть ли под заголовком хоть один вопрос», и на
  живом состоянии 2026-08-06 там стояли шестнадцать строк, из которых
  пользователю принадлежали три: остальное — наши продуктовые решения, вопросы
  к исполнителю про его среду, уже починенный `repo-health` и вопросы, на
  которые пользователь ответил письмом. Он сказал об этом прямо: «Я ответил на
  все запросы. И ты пишешь в письмах по направлениям, что от меня ничего не
  требуется. Расхождение.» Разбор по строкам —
  `python3 scripts/process_map_state.py --questions`.

  Из этого следует обязанность записи: решение, без которого работа не может
  идти, пишется вопросом в задаче или строкой в `## Открытые вопросы` продукта,
  а вынесенное человеку — с пометкой о дате, канале и сообщении. Утверждение в
  свободном тексте доска ожиданием ответа не считает и не угадывает; фраза
  «решение за пользователем» пометкой не является.
- **«Сделано, но не доставлено» — это завершённая работа без свидетельства
  вручения.** Признак наблюдаемый: задача терминальна, в каталоге лежит документ
  для человека (файл в `deliverables/` или `*.html` в самом каталоге), и при этом
  нет ни записки о доставке (`delivery.md`, `product-owner-delivery.md`), ни
  записанного решения не доставлять отдельно (`product-owner-decision.md`), ни
  квитанции о документе. Квитанции жизненного цикла
  прогона свидетельством не считаются: у 783 их было две — «работа началась»
  18447 и «работа кончилась» 18479, — а отчёт на 441 КБ пролежал на сервере час,
  и заметил это не контур, а пользователь. Это единственная область, которая
  читается сверху вниз от свежего к старому: у старой завершённой задачи
  документ либо давно унесли иначе, либо он перестал быть нужен, а ждут прямо
  сейчас тот, что только что появился.
- **«Готово к запуску» — это записанное условие, которое перестало держать.**
  Условие запуска пишется машиночитаемо в то же поле `status_detail`, которым
  уже объясняется, почему задача стоит, и тем же единственным интерфейсом
  (`tasks_index.py set-status <номер> planned --detail "…"`). Грамматика
  маленькая: `starts_after=830` — после каких задач, `worktree=/path/to/example` —
  какое рабочее дерево задача занимает, через пробел в любом порядке. Наблюдатель
  проверяет её сам: названная задача не терминальна — держит; названное дерево
  занято живым прогоном — держит; названной задачи нет в каталоге — тоже держит,
  потому что ненаблюдаемое не то же самое, что законченное, и опечатка в номере
  не имеет права двигать очередь. Когда не держит ничего, задача уходит из
  «В очереди» в «Готово к запуску» — это уже, а не «можно подхватить»: там стоит
  работа, о которой заранее сказали, когда её можно начинать, и этот момент
  наступил. Проза в том же поле ведёт себя как прежде — непрозрачное удержание в
  словах автора: наблюдать, когда предложение перестало быть верным, нечем.

  Цена отсутствия: 2026-08-06 задача 831 несла условие последней строкой своего
  `## Summary` — «после завершения прогона 830, то же рабочее дерево». 830

- **Очередь принадлежит плану, а не наблюдению.** «В очереди, за чем стоит» и
  раздел «В очереди» над колонками читают одно и то же — действующую редакцию
  портфельного плана (`product_memory.current_plan()`, поле `next`), — и порядок
  на доске совпадает с ней поимённо. Владелец назван прямо в шапке раздела и на
  каждой плашке («9-я в очереди плана»), потому что вывести очередь из
  наблюдения нельзя: `planned` — это статус, и план говорит об этом сам последней
  своей строкой («не является очередью: все прочие задачи со статусом planned»).
  Раздел показывает голову каждого списка, а хвост складывает и называет своё
  число («ещё строк редакции: 18»): раздел стоит над колонками, и развёрнутым он
  уводил «В работе сейчас» на пятый экран телефона. Ни строки при этом не
  теряется, а раскрытое переживает живое обновление страницы.
  Место в очереди и «за чем стоит» — два разных поля и два разных утверждения:
  держатель наблюдается (живой прогон в том же дереве, незакрытая
  предшественница), а место назначено, и тот же план разрешает направлениям
  идти параллельно, так что работа выше по списку никого не держит. Наблюдение
  старше плана: задача, которую редакция ставит в очередь, а наблюдение видит
  живой, закрытой или в заторе, стоит в наблюдаемой области, и место в плане
  остаётся на её плашке — расхождение видно, а не примирено. Строка плана, за
  которой не удалось наблюсти задачу, показывается целиком и помечается «связь
  с задачей не установлена».

  Предметом строки считаются только номера в её начале, до тире, — «1121 —
  первый живой запуск…», «1125 и 1134 — довести…», — и они сверяются с каталогом
  задач. Число дальше по строке предметом не является ни в одном поле редакции:
  независимое ревью показало, что строка «Клиент — 1152 … порядок 1150 → 1151
  → 1152» записывала в паузу 1150 и 1151, названные там порядком, а строка
  «исследование 1150 и 1151 разрешено» — работу, которую пользователь как раз
  разрешил. Строка, которая начинается не с номера, стоит на доске своим текстом
  и без задач за ней. Названные ею задачи при этом не пропадают: они перечислены
  рядом отдельно («также названы: #1054 (в очереди), #1067 (в очереди)»), и на
  плашке такой задачи стоит «план называет её в строке, но не её предметом», а не
  «план о ней не говорит», — второе было бы неправдой. Область такой задаче это
  не меняет: она стоит там, куда её ставит наблюдение или её собственная строка
  плана.

  Правило одно и то же во всех областях: место — очередь или пауза — назначает
  только предмет строки, упоминание не назначает ничего нигде. Несимметричный
  вариант («держащая строка держит любой названный ею номер») был введён и снят:
  независимое ревью показало на живом снимке, что разрешающая строка
  «исследование 1150 и 1151 разрешено» объявляла остановленной прямо разрешённую
  пользователем работу и убирала её из доступной. Страховка от неудачной
  формулировки принадлежит плану, а не доске: работу, которую держит чьё-то
  слово, план называет отдельной строкой со своим номером в начале — «одна
  строка плана, одна задача» (редакция 34).

  План, сказавший об одной работе двояко — предметом строки очереди и предметом
  держащей строки, — обе строки показывает. Побеждает более конкретное
  утверждение — очередь, — а на плашке стоит «план и ставит её в очередь, и
  держит её другой своей строкой; место оставлено за очередью», и обе строки
  лежат в источниках. Молчаливый выбор одной из двух несовместимых строк однажды
  показал 1054 и 1067 бэклогом через сутки после того, как пользователь снял их
  с полки.

  Второго вида — «неразобранного» — здесь нет намеренно, и требование снято

  автоматом, поэтому область о ней солгала бы дважды. Задача, которой в плане

  Дословно пользователь: «панель показывает, что в работе ничего нет. При этом
  не сделанных задач — вагон… Тогда почему ничего не делаешь?». Дребезг лечится

  `PRODUCT_OWNER_IDLE_REMIND_SECONDS` (по умолчанию час), изменившаяся — сразу.
  «Сделано, но не доставлено» дольше `PRODUCT_OWNER_UNDELIVERED_SECONDS` будит

- **Причина простоя называется словами и уходит и в панель, и в письмо.**
  Наблюдаемые виды: занят другой продакт, занято рабочее дерево, исчерпано
  недельное окно Codex (а значит, по работе Claude нет проверяющего), ждём
  ответа пользователя. Когда ни одна не сработала, это тоже пишется вслух —
  «причина простоя не наблюдается, значит запускать надо», и на доске это не
  очередная серая строка. Пустая клетка вместо причины считается дефектом.

  **Причина обязана относиться к той работе, которую объясняет.** Первые три
  вида держат всё направление сразу, а «ждём ответа пользователя» держит ровно
  те задачи, по которым вопрос задан, — и области доски не пересекаются, так что
  задача с вопросом заведомо не лежит ни в «можно подхватить», ни в «готово к
  запуску», ни в «решено и не исполнено». Поэтому вопрос называется причиной
  только тогда, когда свободной работы в направлении нет; рядом со свободной
  работой он объяснял бы девять задач десятой и вдобавок глушил бы честное
  «значит запускать надо».
- **Панель говорит, когда продакт проверит статус в следующий раз, когда
  проверял в прошлый и чем та проверка кончилась.** Это два наблюдения, а не
  одно, и снимаются они в разные моменты.

  Прошлая проверка — блок `check`, который тик пишет в
  `state/threads/<тред>.json` в момент проверки, а не проза разбуженного агента:
  итог берётся из разницы живых прогонов до и после пробуждения («запустил 3 —
  задачи …», «не нашёл, что запустить, хотя работы к запуску 9», «жду ответов на
  вопросы пользователю»).

  Следующая проверка — это `NextElapseUSecRealtime` таймера, то есть то, на что
  systemd его действительно взвёл, и больше ничего. Вычислять за systemd
  ближайшую минуту по `OnCalendar` — хоть через `systemd-analyze calendar`, хоть
  через `next_elapse=` внутри `TimersCalendar` — запрещено: календарь отвечает
  «когда сработало бы такое расписание», systemd отвечает «на когда взведён этот
  таймер», и у проверки, пережившей свой двадцатиминутный шаг, это разные
  минуты.

  **Спрашивается это при сборке снимка (`process_map_state.next_check`), а не
  тиком.** Тик — это и есть сервис, парный таймеру, поэтому единственный момент,
  когда он мог бы записать поле, — единственный момент, когда таймер заведомо не
  взведён. Ревью 900 нашло ровно это: во всех четырёх живых файлах состояния
  стояло «неизвестно», пока systemd держал настоящие будущие времена для трёх из
  них. Вопрос «когда проверит в следующий раз» — про настоящий момент, поэтому
  на него отвечает тот, кто собирает доску, в момент запроса. Побочно это даёт
  ответ и по направлению, по которому тик не писал ещё ни разу.

  Когда systemd ничего не держит взведённым — обычно потому, что проверка этого
  направления идёт прямо сейчас, — показывается «неизвестно», **а рядом обычным
  видимым текстом то, что наблюдено вместо времени**. Не в атрибуте `title`:
  подсказку по наведению телефон и планшет не показывают вовсе, так что строка
  обещала бы объяснение и отдавала бы его только владельцам указателя (замечание
  MEDIUM-1 того же ревью).

  Причины простоя показываются только у проверки, которая закончилась и ничего
  не запустила. Это решает поле `started` с тремя ответами: `null` — продакт ещё
  решает, пустой список — не стал запускать, непустой — запустил. Без него
  колонка показывала «запустил 3 — задачи 823, 872, 873» и «причина простоя не
  наблюдается» разом.

  Файл состояния — рантайм, и его пересобирает следующий тик, поэтому запись, не
  сходящаяся с контрактом, доску не роняет: показывается третий ответ — «запись
  прошлой проверки не читается» с названным расхождением. Это не то же самое,
  что «проверок не было».
- **Уступать дорогу надо тому, кто может занять то же рабочее дерево.** Не
  любому бодрствующему продакту: четыре направления владеют четырьмя
  непересекающимися наборами репозиториев, а четыре таймера были заведены с
  одним `OnUnitActiveSec=20min` и просыпались в одну секунду. В записях за
  2026-08-07 16:06 это видно прямо — `client` уступил `process`,
  `platform` уступил `client` и `process`, `product` уступил всем троим, у
  `process` уступать было некому. Действовать мог ровно один тред, и всегда один
  и тот же. Теперь таймеры разнесены по минутам внутри двадцатиминутного шага
  (`systemd/product-thread@<тред>.timer.d/offset.conf`, `OnCalendar=*:MM/20`), а
  уступают только при общем рабочем дереве.
- **Бодрствовать и решать — разные состояния.** Дорогу уступают тому, кто может
  занять то же дерево *и работает*: терминал, которому работу уже передали,
  иначе держал бы фоновую цель столько, сколько живёт процесс, — то самое
  «приходилось следить за доступностью терминала». Наблюдение — разница
  процессорного времени процесса (`/proc/<pid>/stat`) между двумя наблюдениями
  тика, и записывает её только тик: панель перестраивается каждые несколько
  секунд и объявила бы неработающими всех. Первое наблюдение разницы не имеет и
  считается работой. Кому не уступили — видно в `not_yielded_to`.
- **Цель направления видна в шапке колонки.** Обещанный пользователю результат,
  пометка усиленного контроля, ближайший разрыв, основная задача с её паузой,
  корректирующие задачи с их состоянием и следующий переход. Это не наблюдение
  процесса, а продуктовая память, поэтому читается из своего долговечного
  хранилища (`content/goals/`), и контракт снимка держит то же правило, что и
  плашки: цель без источника наблюдения или корректирующая задача без критерия
  возврата на панель не попадают. Устройство — `docs/goal-control.md`.
- **Под целью видно, кто её ведёт.** Живая непрерывная сессия с числом ходов и
  временем реакции последнего — или прямо сказанное «непрерывной сессии нет,
  ведёт двадцатиминутный тик» с причиной. Пока строка говорит «ведёт сессия»,
  тик сознательно молчит, поэтому контракт требует назвать, чем живость
  наблюдена, и отказывает живой сессии без идентификатора разговора.
- **«Другой я» показывает фоновый тик, почтового и консольного продакта.**
  Стоит он в полосе-сводке, но за переключателем источников: сообщение «может
  занять product-owner — сверьтесь с его очередью, прежде чем заводить задачу»
  адресовано другому агенту, и места на первом экране человека ему не
  полагается (задача 1163). Признавался только тик — процесс с `thread_tick.py` в argv, — и именно поэтому
  поле никогда не было заполненным: такой процесс без событий живёт около
  секунды на двадцать минут, а консольный продакт работает часами и не совпадал
  ни с чем. Тик опознаётся ещё и по своему исполняемому файлу, иначе обёртка
  вроде `timeout 600 python3 …/thread_tick.py process` считается продактом.
  Почтовый экземпляр отличается наблюдаемой цепочкой родителей через
  `mail_product_owner.py`; консольный — явным именем роли Claude или стартовой
  командой Codex. Node-обёртка и её нативный Codex считаются одной сессией, а
  Codex-ребёнок задачи с тем же cwd продактом не объявляется. Каждый названный
  несёт рабочие деревья, которые может занять, — это и есть то, ради чего строку
  читают.
- **Процесс завершённой задачи остаётся в состоянии треда.** Наблюдатель связывает
  его с задачей только в том направлении, куда задачу относит её проектная
  ссылка в индексе; общий путь `task-agent/tasks` принадлежностью к
  `process` не считается. Репозиторий подтверждается внешними признаками `/proc`
  — cwd, argv, exe и открытыми файлами вне общего хранилища задач. Выходной файл называется по открытому writable fd либо
  по mtime файла рядом с cwd задачи, если append успел закрыться между сканами.
  `thread_state.py` хранит прошлый размер в `state/process-inventory/` и поэтому
  говорит о росте только после двух измерений. Одинаковые задача, репозиторий и
  команда образуют явную группу дублей. Тик сохраняет полную опись в своём
  `state/threads/<тред>.json` и будит продакта, когда такой процесс появился,
  исчез или число дублей выросло; рост самого журнала на каждом опросе новым
  событием не считается. Зарегистрированные child/watcher-процессы раннера и их
  потомки остаются только живым прогоном даже после ранней терминальной метки
  задачи и второй раз в этой описи не появляются.
- **«Без изменений N» измеряет то, что говорит:** mtime самого свежего из файлов,
  от которых зависит область (`task.md`, `status.json`, `verification.md`,
  `.runner/runner.json`). Это верхняя граница момента перехода, а не сам переход;
  сборщик памяти о прошлом состоянии не имеет и не заводит.
- **Живой прогон — это процесс задачи, а не занятый номер.** Ответ берётся у
  раннера (`task_runner.process_is_live`), который сверяет pid со стартовым тиком
  ядра. Нет записанной личности — не жив. Что делать с чужим пространством имён
  PID, решает тот же раннер (`task_runner.runner_pid_namespace_state`): пока
  пространство живо или его отсутствие недоказуемо отсюда — «личность
  ненаблюдаема», а не «процесса нет»; доказанно исчезнувшее пространство имён
  не может держать процессов, и записанный в нём прогон мёртв. Все имена,
  которые доска берёт у раннера, под скан-проверкой `scripts/runner_contract.py`,
  и её зовёт не только тест, но и каждое пробуждение направления — переименование
  в task-agent обязано падать юнитом и уходить письмом, а не слепой панелью
  (задачи 951 и 961). Полная опись связей — ниже.

## Чем этот репозиторий держится за task-agent

Продакт наблюдает работу, которая происходит в чужом репозитории, и потому
зависит от него в четырёх разных смыслах. Разряды не равноценны: только первый
ловится машиной, остальные расходятся молча и обнаруживаются работой. Опись
собрана сканом на 2026-08-08 (задача 961, находка MEDIUM-2 ревью 954) и должна
пересобираться сканом, а не памятью.

**1. Импортируемые символы Python — под автоматической проверкой.**
`process_map_state` кладёт `skills/task-runner/scripts` в `sys.path` и импортирует
`task_runner` через `liveness_owner()`. У него берутся `process_is_live` и
`runner_pid_namespace_state` (в тестах ещё `process_identity`), а из ответов
второй функции разбираются состояния `local` и `recorded_namespace_absent`. Имя
модуля, все заимствованные функции и словарь ответов сверяются
`scripts/runner_contract.py` перед каждым тиком и в тестах.

Второе заимствование — необязательное и безымянное в этом репозитории: опись
живых прогонов. Установка может назвать ключом `run_registry_module` свой модуль
рядом с раннером, у которого берётся `live_run_processes` — identity-проверенная
опись зарегистрированных child/watcher-процессов, которые нельзя второй раз
показать как пережившие задачу. Установка, которая не называет ни одного, —
рабочая установка: `runner_contract` пишет отдельной строкой «не установлено в
этой установке», ручное состояние прямо помечает опись недоступной, а тик
удерживает последнюю наблюдённую опись и её availability marker. Отсутствие
наблюдения не превращается ни в пустой список, ни в ложное событие смерти
процесса, и тревога тика остаётся тревогой про переименование. Модуль, который
назван, стоит на месте и потерял имя, — по-прежнему нарушение: ради этого случая
проверка и написана.

Третье заимствование — защита перед push. `hooks/pre-push` загружает
`skills/repo-health/scripts/check_pre_push.py` той установки, которую называет
`leak_check_repo` (по умолчанию `tasks_repo`), и берёт у него `main`, `repo_root`,
`default_base`, `private_history_markers`, `private_history_match` и
`SECRET_PATTERNS`. Проверяется не автоматической сверкой, а самим hook перед
каждым push: недостающее имя — это названный отказ push, а не тихо ослабленная
проверка. Второй реализации файлового скана здесь нет намеренно; своё у hook
только то, чего у владельца нет вовсе, — чтение личности и сообщения исходящих
коммитов.

**2. Интерфейсы командной строки — не закрыты.** Ошибка приходит в момент
работы, а не проверки.
- `tasks_index.py query --format json --limit` с флагами `--status`, `--project`,
  `--search` (`process_map_state.query_tasks`). Самая дорогая связь: весь каталог
  задач доски — это один такой запрос. Из его выдачи читаются поля `path`, `dir`,
  `id`, `slug`, `title`, `status`, `status_detail`.
- `gmail-client/scripts/send_email.py --to --subject --body`
  (`thread_tick.send_mail`) — единственный канал, которым продакт что-либо
  говорит пользователю.
- `git -C <репозиторий> log/status` по репозиториям направлений
  (`process_map_state`, `process_map_recorder.observe_commits`) — сам репозиторий
  системы задач тоже наблюдаемый, если направление им владеет.
- Интерпретатор `<система задач>/.venv/bin/python` — а если его нет, тот, которым
  запущен сам продакт. Корень системы задач не зашит в код: его называет
  установка ключом `tasks_repo` в `threads.json` или переменной
  `PRODUCT_OWNER_TASKS_REPO`, а владелец ответа один — `product_memory.tasks_repo()`
  (`process_map_state.py`, `product_goal.py`, `thread_tick.py`). Ненаблюдаемый
  корень — это отказ по имени, а не пустой каталог задач: `query_tasks`
  поднимает `ContractError`, и доска говорит «спросить некого» вместо «задач
  нет».

**3. Схемы и раскладки артефактов задачи — не закрыты.** Читаются с диска
напрямую, поэтому переименование ключа или перенос файла меняет смысл показанного,
не ломая ничего заметно.
- `task.md`: frontmatter (`id`, `title`, `slug`, `status`, `status_detail`) —
  `process_map_state`, `process_map_recorder.read_frontmatter`; раздел
  `## Summary` — `process_map_state.summary`; раздел `## Open Questions` —
  `process_map_state`.
- `plan.md` — классифицируется как «анализ» при обходе артефактов
  (`process_map_recorder`).
- `status.json`: `state`, `current_step`, `runner`, `workflow`, `pid`,
  `completion_refusal.kind`, `completion_refusal.summary|reason`.
- `progress.json`: `activity`, `completed`, `total` (свежесть — из mtime, и это
  намеренно).
- `.runner/runner.json`: `pid`, `process_identity`, `pid_namespace`, `runner`,
  `sandbox_mode`, `access_grant.sandbox_mode`, `access_grant.granted_directories`,
  `watcher_pid`, `watcher_process_identity`, `watcher_stop_reason`, `exit_code`,
  `command`, `started_at`, `--repo`. Через `live_run_processes` описи живых
  прогонов наблюдатель получает записи `role`, `pid`, `evidence` и использует
  `pid` как корень внешне наблюдаемой цепочки процесса.
- `verification.md`: строки `Result: OK|GAP|BLOCKED|FAIL`; `findings.md`: строка
  `Verdict:` и заголовки находок.
- `deliverables/` и `*.html` в каталоге задачи — то, что считается документом для
  человека; `manifest.json` документом не считается.
- Список «бухгалтерских» имён `status.json`, `progress.json`, `task.md`,
  `task_contract.json` и правило «прочее в каталоге задачи — артефакт»
  (`process_map_state.artifact_movement`, `process_map_recorder`).
- Раскладка dev-pipeline: `dev-pipeline/core/events.jsonl` (`kind`, `runtime`),
  `dev-pipeline/notification-receipts.jsonl` (`kind`, `message_id`,
  `recorded_at`); обе читаются с байтового курсора.
- Почтовая раскладка `.state/gmail/product-owner/{inbox,sent}`
  (`process_map_state`, `process_map_recorder`).

**4. Настроенные и задокументированные операционные вызовы — не закрыты.**
Расхождение здесь ломает не наблюдение, а способность продакта отдать работу.
- `docs/handing-work-to-development.md` (на него ссылается `AGENTS.md`) дословно
  называет `tasks_index.py add "Заголовок" "Суть" слаг [--project ...]` и
  `task_runner.py start tasks/<id>-<слаг> --repo <репозиторий>`, включая правило
  «`--project` — путь к файлу, а не слаг». Ручного `--destination` в штатном
  вызове нет: разрешённый адрес уведомлений выдаёт серверный владелец
  credentials, и подстановка адреса руками — признак обхода профиля, а не
  нормальный путь.
- `.claude/settings.json` разрешает ровно эти два вызова через
  `task-agent/.venv/bin/python` — переименование скрипта или его переезд
  снимает разрешение вместе с возможностью запускать работу.
- `AGENTS.md` ссылается на файл пользовательских предпочтений системы задач
  (`tasks/USER_PREFERENCES.md` в ней) как на источник пользовательских указаний.
- `threads.json` держит корень системы задач и её же репозиторий в направлении,
  которое за неё отвечает.
- Юниты `product-thread@.service` и `product-owner-board.service` фиксируют
  рабочий каталог и точки входа, из которых всё перечисленное вызывается. Имя
  первого из них доска знает не только чтением: `state.wake_unit()` строит его,
  чтобы спросить systemd, идёт ли проверка, и чтобы кнопка «продолжить сейчас»
  запускала ровно ту единицу, которую заводит таймер. Переименование шаблона
  юнита снимает и наблюдение, и кнопку.

Второго сломанного символа на 2026-08-08 в описи нет: разряд 1 сходится, вызовы
разряда 2 существуют, разряды 3 и 4 сверены чтением. Но «сходится сегодня» — это
не «под охраной»: закрыт автоматом только первый разряд.
- **`--anonymize` — свойство показа, а не происхождения файла.** Снимок и лента
  чистятся на пути к странице, кем бы они ни были записаны. Очистка идемпотентна;
  восстанавливать исходные значения после неё нельзя ни одному вызывающему.
  Границы очистки структурные: пути, почта, длинные идентификаторы и числовые
  ключи-идентификаторы. Содержательная приватность заголовков остаётся шагом
  человека перед показом и объявлена ограничением.
- **«Надо запланировать» показывает несостоявшуюся сверку, а не отсутствие
  работы.** Строка раздела `## В работе` уходит с доски, когда за ней наблюдена
  задача, и признак наблюдения один — `promise_link()`: номер, стоящий в строке
  как ссылка на задачу (в скобках, после слова «задача», в начале утверждения) и
  найденный в каталоге; дословное название задачи или её слаг в строке; либо
  число, подтверждённое половиной значимых слов названия той же задачи. Всё
  остальное показывается со словами «связь с задачей не установлена» и со
  сверкой, которая не сошлась. Сказать «задачи нет» доска не вправе: до правки
  признаком непоставленности было «в строке нет трёхзначного числа», и он врал в
  обе стороны сразу — три из четырёх показанных строк уже имели задачи, а
  настоящее обещание пропадало из-за постороннего числа вроде «394 теста»
  (находка HIGH-1 ревью 814). Всю сверку построчно печатает
  `process_map_state.py --plan-links`.
- **Наблюдение не дорожает от объёма работы.** Транскрипты детей не читаются
  никогда; журналы — от байтового смещения; каталог задачи обходится на два
  уровня по именам, а не по содержимому. Связь продуктовой строки с задачей
  строится только по каталогу задач (один запрос `tasks_index.py query`) и по
  тексту самой строки — ни одного открытого файла задачи.
- **Ни один срез не молчит о том, что скрыл.** Каждый предел («показано 25,
  скрыто 39», «названо 4 из 6») подписан в самом заголовке.
- **Доска светлая и прокручивается; ничего не режется.** Ни у плашки, ни у
  области, ни у колонки, ни у карточки нет своей полосы прокрутки — скроллится
  страница, и длинный текст делает плашку выше, а не прячет свой хвост. Второй
  палитры больше нет: тёмная принадлежала холсту карты и ушла вместе с ним.
  Требование пользователя дословно: «не надо стараться всё упихнуть в экран… а
  то так ничего не понятно: микроплашки с микроскроллом». Измеряется браузером,
  а не чтением стилей: `tasks/817-board-light-theme-and-human-truth/render.sh`
  считает на 1440×900 и 390×844 элементы со своей прокруткой, обрезанный текст и
  всё, что уехало за окно, и требует нулей. Сколько строк берёт лента сверху —
  тоже измерение, а не вкус: двенадцать занимали 300 px из 900 и 1500 px из 844,
  и всё, ради чего доска существует, начиналось под ними; шесть оставляют первый
  экран ответам, над которыми стоят.
- **Обновление данных не двигает страницу под читателем.** Живой режим
  опрашивает сервер каждые десять секунд и перерисовывает доску на месте:
  открытая карточка остаётся открытой на той же задаче **и на той же позиции
  прокрутки**, свёрнутые области остаются свёрнутыми. Возврат карточки к началу
  на каждом опросе — та же помеха, что и `location.reload()`, от которого уже
  отказались. «Старшая: N» — сравнение, поэтому в области с одной плашкой не
  показывается вовсе: возраст единственной задачи стоит на ней самой.
- `scripts/codex_budget.py` — остаток недельного окна подписки Codex.
- `scripts/lesson.py` и `lessons/` — уроки: что наблюдалось, чего это стоило,
  какое правило следует и в какого владельца урок унесён. Механизм в git, сами
  уроки — нет: это дневник одной установки про одного пользователя.

## Чего здесь нет

Правил исполнения задач, профилей, гейтов и жизненного цикла. Они живут в
системе задач и применяются там, куда работа реально уходит. Продакт не
правит код продуктов своими руками.

Рантайм-состояние (`state/`) не отслеживается: оно пересобирается наблюдением
на каждом тике и не является записью решения.

Содержания и настроек одной установки: `content/` (снимки продуктов, план,
решения, цели), `threads.json`, `lessons/` и смещения таймеров реальных
направлений. В git лежат механизм и шаблон — `threads.example.json`, шаблон
снимка внутри `product_memory.py`, пример смещения таймера, — а ответы
принадлежат установке. Поэтому клон этого репозитория не несёт ни одной чужой
продуктовой записи.
